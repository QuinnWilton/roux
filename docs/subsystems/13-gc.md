# Subsystem: Garbage collection

Module: `Roux.GC`

## Purpose

Clean up stale memo entries and dead entities from ETS tables. Without GC, a long-running LSP server accumulates unbounded dead state over hundreds of edits. Elixir's garbage collector handles process heap data, but ETS entries persist until explicitly deleted.

## Dependencies

- `Roux.Database` — table references
- `Roux.Memo` — memo entry reads and deletes
- `Roux.Entity` — entity table cleanup, refcount operations

## Key types

```elixir
@type sweep_result :: %{
  memo_entries_removed: non_neg_integer(),
  entities_removed: non_neg_integer(),
  duration_us: non_neg_integer()
}
```

## Public API

```elixir
@spec sweep(Roux.Database.t()) :: sweep_result()
# Perform a garbage collection sweep.
# Deletes all entities with refcount == 0 and orphaned memo entries.
# Returns statistics about what was cleaned.

@spec sweep_query(Roux.Database.t(), Roux.Memo.query_key(), old_entities, new_entities) :: :ok
# Diff a query's output entities after re-execution.
# Decrements refcounts for entities in old but not new.
# Increments refcounts for entities in new but not old.
# Called by Runtime after a query re-executes.

@spec mark_input_removed(Roux.Database.t(), input_name :: atom(), key :: term()) :: :ok
# Mark an input as removed (file deleted). The memo entry is deleted
# and downstream queries are candidates for GC.
```

## Entity reference counting

Each entity has a reference count tracking how many queries include it in their `output_entities` set. This is an integer field in the entity's ETS row (or a dedicated `:atomics` per entity).

See decision [D15](../decisions.md) for rationale on building this in from the start.

### Lifecycle

**Entity created by a query for the first time:**
1. Runtime flushes the query's output entities to the memo entry.
2. `sweep_query/4` is called with `old_entities = []`, `new_entities = [entity]`.
3. Entity's refcount increments from 0 to 1.

**Second query also creates the same entity:**
1. `sweep_query/4` called with that query's old/new diff.
2. Entity's refcount increments from 1 to 2.

**One query stops producing the entity (re-executes, entity not in new output set):**
1. `sweep_query/4` called: entity is in old but not new.
2. Entity's refcount decrements from 2 to 1. Entity survives.

**Last query stops producing the entity:**
1. Refcount decrements from 1 to 0.
2. Entity is a candidate for deletion. Either:
   - Delete immediately (eager), or
   - Delete on next `sweep/1` call (lazy).

Lazy deletion is safer — it avoids races with concurrent readers. The periodic sweep collects all zero-refcount entities.

### Refcount storage

Two options:

**(A) Field in entity ETS row**: Add a `__refcount__` field to the entity tuple in ETS. Use `:ets.update_counter/3` for atomic increment/decrement.

**(B) Separate `:atomics` per entity**: One atomics slot per entity. Lock-free, but requires managing the atomics lifecycle alongside the entity.

**Use option A.** `:ets.update_counter/3` is atomic and avoids a second data structure. The refcount is just another column in the entity row.

## GC algorithm

### Per-query GC (after re-execution)

When a query re-executes, Runtime calls `sweep_query/4`:

1. Compute `removed = old_entities -- new_entities`.
2. Compute `added = new_entities -- old_entities`.
3. For each removed entity: `:ets.update_counter(entity_table, entity_id, {refcount_pos, -1})`.
4. For each added entity: `:ets.update_counter(entity_table, entity_id, {refcount_pos, 1})`.

This is O(|old| + |new|) — typically small.

### Periodic sweep

A periodic sweep deletes dead entities and orphaned memo entries:

1. For each entity table: scan for entries with refcount == 0.
2. Delete them from the entity table and their intern table entries.
3. For memo entries: delete entries whose dependencies include deleted entities.
4. Emit `[:roux, :gc, :sweep]` telemetry with statistics.

### Input removal

When `mark_input_removed/3` is called:

1. Delete the input's memo entry.
2. Advance the revision counter (the input "changed" — to nonexistence).
3. The next time downstream queries are requested, validation will find the input missing and trigger re-execution. Re-execution will either fail (if the input is required) or produce different output (if the input is optional), and `sweep_query/4` will decrement refcounts for entities no longer produced.

No eager cascade deletion needed — the normal validation/re-execution/sweep_query cycle handles it.

## Fixed-point iteration interaction

During fixed-point iteration (future, see [D7](../decisions.md)), a query re-executes multiple times with provisional values. Each iteration may produce different output entities, causing refcounts to oscillate:

```
Before cycle: A's output = {X, Y}     refcounts: X=1, Y=1
Iteration 1:  A's output = {X, Z}     sweep_query: Y→0, Z→1
Iteration 2:  A's output = {X, Y}     sweep_query: Z→0, Y→1
Iteration 3:  A's output = {X, Y}     converged, no-op
```

This is safe because of lazy deletion: `sweep_query` adjusts refcounts but never deletes. Only `sweep` deletes, and `sweep` must not run during active query execution (including fixed-point iteration). After convergence, refcounts reflect the correct final state and the next idle sweep cleans up.

If a different query B also references entity Y, Y's refcount never drops below 1 during iteration (B's reference persists). Only entities exclusively owned by the iterating query can temporarily hit 0.

**Invariant**: `sweep` must not run while any query is in a fixed-point iteration loop. The runtime must enforce this (e.g., by tracking active fixed-point cycles and deferring sweep triggers).

## Implementation notes

- GC should never delete entities with refcount > 0. This is the core invariant.
- `sweep/1` should run on an idle timer (e.g., after 60 seconds of no input changes) or on explicit trigger. Not after every query.
- `sweep_query/4` runs after every query re-execution — it must be cheap. The set diff + `update_counter` calls are O(output set size), which is typically small.
- Entity deletion must be careful about concurrent reads. A reader that races with deletion gets `:miss` from ETS and triggers recomputation — this is safe.
- `:ets.update_counter/3` is atomic, so concurrent refcount updates from parallel queries are safe without additional locking.
- `sweep/1` should emit `[:roux, :gc, :sweep]` telemetry events with statistics.

## Testing strategy

### Unit tests
- Entity created → refcount is 1
- Second query creates same entity → refcount is 2
- One query stops producing entity → refcount decrements to 1, entity survives
- Last query stops producing entity → refcount is 0, sweep deletes it
- Sweep with no zero-refcount entities → nothing deleted
- Input removed → downstream queries re-execute and adjust refcounts
- `update_counter` atomicity: concurrent increment/decrement produces correct count

### Integration tests
- Long sequence of edits: verify entity table size stays bounded
- Sweep produces correct statistics
- Entity with refcount 0 is deleted, entity with refcount > 0 survives

### Property tests
- For any sequence of input additions, modifications, and removals, all live entities have refcount > 0 and all dead entities have refcount == 0
- Refcount equals the exact number of memo entries that include the entity in their output_entities

### Concuerror tests
See decision [D11](../decisions.md).
- Concurrent `sweep_query` calls on different queries both decrementing the same entity → final refcount is correct
- `sweep` racing with `sweep_query` → no double-free, no missed deletions
